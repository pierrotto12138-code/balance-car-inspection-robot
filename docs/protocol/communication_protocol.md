## 一、物理层

| 项目 | 约定 |
|---|---|
| 链路 | **经典蓝牙 SPP**（机器人端接 USART2，即 PA2/PA3） |
| 波特率 | **115200 bps**（⚠️ 基底原为 9600，需用 AT 指令把蓝牙模块改到 115200） |
| 帧格式 | 8 数据位，无校验位，1 停止位（**8N1**） |
| 调试备选链路 | USART1（PA9/PA10，原厂 128000，有线 USB-TTL）——仅供调试，不作为交付链路 |

> **为什么选蓝牙 SPP**：模块被系统枚举为虚拟串口，上位机用 `QSerialPort` 直接读写，
> 无需协议栈开发；相比 BLE 的 GATT（Windows 端支持不佳）与 WiFi 组网（需现场配 AP），
> 在三周项目里实现成本最低。

### 1.1 与基底原有通信的关系

基底已有的通信通道（需在改造时清理或共存）：

| 通道 | 用途 | 处置 |
|---|---|---|
| USART2 单字节 APP 指令（`uart_receive`） | 厂商手机 APP 遥控 | **替换**为本协议 |
| USART1 + DataScope（`$` 帧 + float 数组） | 厂商 PC 上位机看波形 | **保留**为调试通道，由 `Flag_Show` 切换 |
| 航模遥控（PC6/PC7，TIM8 输入捕获） | 遥控器 | 保留，可作演示备份 |

## 二、帧格式（通用）

所有帧（上行、下行）采用同一结构：

| 字段 | 长度（字节） | 说明 |
|---|---|---|
| 帧头 | 2 | 固定 `0xAA 0x55` |
| 命令字 | 1 | 标识帧类型，见第三、四节 |
| 数据长度 | 2 | N，数据段字节数；**小端**（低字节在前） |
| 数据段 | N | 各命令定义（可为 0） |
| 校验 | 2 | **CRC-16/MODBUS**，覆盖范围：**命令字 → 数据段末尾**（即偏移 2 起，共 1+2+N 字节） |

**帧总长** = 2 + 1 + 2 + N + 2 = **7 + N**

### 2.1 CRC-16/MODBUS 算法约定

- 多项式：`0xA001`（即 CRC-16/IBM 的反转形式）
- 初始值：`0xFFFF`
- 输入/输出反射：是（该算法即按位右移实现）
- 结果异或：`0x0000`

参考实现（C）：

```c
uint16_t crc16_modbus(const uint8_t *buf, uint16_t len)
{
    uint16_t crc = 0xFFFF;
    while (len--) {
        crc ^= *buf++;
        for (int i = 0; i < 8; i++) {
            if (crc & 0x0001) { crc >>= 1; crc ^= 0xA001; }
            else              { crc >>= 1; }
        }
    }
    return crc;
}
/* 发送时低字节在前 */
```

**校验用例**（已用上述实现实算，不是估计值；双方各自实现后须对同一组数据复现）：

| 自检项 | 输入 | 期望 CRC-16/MODBUS |
|---|---|---|
| **算法自检（标准）** | ASCII `"123456789"`（9 字节） | **`0x4B37`** |
| 用例 1 | `10` | `0x8CBE` |
| 用例 2 | `10 0C` | `0x750C` |
| 用例 3 | `10 0C 00` | `0x0575` |

> **第一条是 CRC-16/MODBUS 的标准校验值**（ASCII "123456789" → 0x4B37），
> 用来确认多项式与初始值实现正确；后三条用于确认字节序处理一致。
> ⚠️ **待办**：B/C 双方各自实现后须逐条复现上表，全部一致方可冻结。

### 2.2 接收端状态机

```
等待帧头 → 收第 2 字节(须为 0x55) → 收命令字(1B) → 收长度(2B) →
收数据段(N) → 收 CRC(2B) → 校验 → 通过则投递，否则丢弃并重新同步
```

**要点**：
- 必须有**长度字段**，不能用"扫描帧尾"的方式（float 数据里可能出现任意字节）；
- 校验失败时**丢弃整帧**并从头找下一个 `0xAA`（不要只丢 1 字节，避免连带丢失）；
- 接收超时保护：单帧接收超过 **100 ms** 未完成则复位状态机。

## 三、上行帧（机器人 → 监控系统，命令字 0x10–0x1F）

| 命令字 | 名称 | 长度 N | 数据段定义 | 周期 |
|---|---|---|---|---|
| 0x10 | 姿态数据 | 12 | 俯仰角 int16(0.01°)（= 平衡角）、**横滚角 int16(0.01°) = 左右倾角**（★ v1.2 更正：2026-10-15 前固件把它写死 0；现取**加速度计 X 轴**算的**静态**倾角 `atan2(Accel_X, Accel_Z)` —— 因为本机 `Way_Angle=2`（卡尔曼）时 `Get_Angle()` 的 DMP 分支从不执行、DMP 的 `Pitch/Roll` 恒 0，详见 `control.c` 的 `Angle_LR`。⚠ 仅加速度计、未做陀螺仪融合，运动时噪声大）、**偏航角恒 0（固件未计算偏航，不编造）**、三轴角速度 int16×3(0.01 dps)（`gx`=前后 / **`gy`=左右** / `gz`=偏航）| 50 ms |
| 0x11 | 运动状态 | **9** | 左轮速 int16(mm/s)、右轮速 int16(mm/s)、**带符号电机输出均值** int16（量程 ≈±8200）、超声波距离 uint16(**mm**)、避障状态位 uint8 | 50 ms |
| 0x12 | 任务状态 | 5 | 任务 ID uint8、阶段枚举 uint8、完成度 uint8(%)、当前巡检点 uint8、异常标志 uint8 | **与 `0x10`/`0x11` 同频（每拍发，节拍由 `CFG_TX_TELEMETRY_MS` 决定，当前 50 ms 标称）** |
| 0x13 | 事件告警 | 5 | 事件码 uint8、时间戳 uint32(ms) | 事件触发立即 |
| **0x14** | **环境与气体** | **16** | **见下** | 常态 1000 ms，异常 200 ms |
| **0x15** | **诊断（v1.2 新增）** | **16** | **见 §3.4** | 1000 ms（**联调专用**）|
| **0x16** | **三环实况（v1.2 新增）** | **20** | **见 §3.5** | 1000 ms（**调参专用**）|
| 0x1F | 心跳 | 0 | 无数据段 | **200 ms（5 Hz）** |

> ⚠ v1.2 更正（2026-10-15，以已烧录代码为准）——本表按代码逐条复核，四条结论：
> **① `0x11` 偏移 6 的"距离"单位是 `mm`，不是 `cm`。** 代码：`timer.c:87` 的 `Distance=Distance*170/1000`
> （TIM3 捕获按 `main.c:53` 的 `TIM3_Cap_Init(0XFFFF,84-1)` = 1 µs 计数 ⇒ 每 1 µs 回波 ≈ 0.17 mm），
> `Distance` 本身就是**毫米**量级；`app_tasks.c:382` 把 `st.distance` **原样**装进该字段
> （固件结构体字段名仍写作 `distCm`，属**命名遗留**，线序与标度不变）。厂商 OLED 代码用 `Distance/10` 显示 cm（`show.c:99`）。
> ⇒ **上位机按 cm 显示需 `/10`。** 标度由厂商常数 `170/1000` 决定，**未按现场声速与安装角标定** ⇒ 绝对值应视为工程近似（本仓库未找到 F1 的时钟配置文件，无法离线核定该常数与实际计数周期的严格关系）。
> 顺带把口径写明：避障判据里的"**500**"就是 **500 mm = 50 cm**（`control.c:205` 的 `Distance<500`，与 `0x11` 距离字段**同单位**）。
> **② `0x11` 的 PWM 字段不是"千分比 0~1000"**，而是**带符号的电机输出均值**（未乘 1.17 的占空比换算，量程 ≈±8200）。
> `app_tasks.c:381` 的 `mot.pwm = (st.pwmLeft + st.pwmRight)/2`，而 `pwmLeft/Right` 就是 `Moto1/Moto2`（`board_state.c:37-38`）——
> `(Moto1+Moto2)/2` 等价于 **Balance+Velocity**（转向分量在求和中抵消），真机实测 −1579。
> **本条推翻了 v1.1 冻结时的"千分比"口径**（§七 约定 4 已同步改写）。
> **③ `0x12` 没有独立的 200 ms（5 Hz）慢节拍**：`0x10`/`0x11`/`0x12` **共用同一个 `telemetryPeriod`**
> （`app_tasks.c:360-390`；`app_config.h:48` 的 `CFG_TX_TELEMETRY_MS=50`）⇒ 三者**每拍同发**；
> 实测真机约 **15 Hz**（受任务节拍影响）。原表"200 ms 或状态变化"已按代码更正。
> **④ `0x1F` 心跳 = 200 ms（5 Hz），复核无误**（`app_config.h:50` 的 `CFG_TX_HEARTBEAT_MS=200`，`app_tasks.c:392-396` 发送）。
> 方向说明：**本表的 `0x1F` 是"机器人 → 上位机"的上行心跳**；上位机保活发的那条"下行 `0x1F`"是**复用同一命令字**另发的帧
> （固件对**任意** CRC 合法下行帧都算"链路活着"，`patrol.c:105-109`），两者不要混为一谈。

### 3.1 0x14 环境与气体（数据段 16 字节）

| 偏移 | 字段 | 类型 | 说明 |
|---|---|---|---|
| 0 | MQ-2 原始值 | uint16 | ADC 原始读数（0–4095） |
| 2 | MQ-135 原始值 | uint16 | ADC 原始读数 |
| 4 | MQ-2 浓度真值 | uint16 | 补偿后浓度，单位 **ppm×10** |
| 6 | MQ-135 浓度真值 | uint16 | 补偿后浓度，单位 **ppm×10** |
| 8 | 环境温度 | int16 | 单位 0.1 ℃ |
| 10 | 相对湿度 | uint16 | 单位 0.1 %RH |
| 12 | 就绪状态位 | uint8 | bit0: MQ-2 就绪；bit1: MQ-135 就绪；bit2: DHT11 有效；bit3: 补偿已启用 |
| 13 | 采样档位 | uint8 | 0=预热中，1=常态 1 Hz，2=异常 5 Hz |
| 14–15 | 保留 | — | 置 0 |

### 3.2 阶段枚举（0x12 第 2 字节）

| 值 | 含义 |
|---|---|
| 0x00 | 初始化 / 自检 |
| 0x01 | 预热中 |
| 0x02 | 待机 |
| 0x03 | 自主巡航 |
| 0x04 | 异常研判 / 驻留加密采样 |
| 0x05 | 返航 |
| 0x06 | 完成 |
| 0x07 | 故障 / 安全停车 |

### 3.3 事件码（0x13 第 1 字节）

| 事件码 | 含义 |
|---|---|
| 0x01 | 上电自检完成 |
| 0x02 | 任务开始 |
| 0x03 | 任务完成 |
| 0x04 | 任务失败 / 超时 |
| 0x05 | 碰撞 / 跌落 / 低电压告警 |
| **0x06** | **气体浓度超阈值** |
| **0x07** | **预热完成 / 传感器失效** |
| **0x08** | **通信失联 → 安全停车**（超过 `linkTimeoutMs`=500 ms 未收到任何下行帧）|
| **0x09** | **安全停车解除**（`0x21` 任务=自主巡航可解除**任何**锁存原因；`0x20` 使能位=1 **仅**解除失联锁存 `LINKLOST`）|
| **0x0A** | **收到急停指令**（`0x2F`）→ 安全停车并锁存 |

> **为什么安全通道单列 0x08~0x0A（决策 57，B 定稿）**：
> `0x12` 是 20 Hz 周期帧，"失联/急停"只体现在它的异常标志与阶段字节里 ——
> 上位机要**对比前后两帧**才能推断出"什么时候停的"，日志会丢时刻。
> `0x13` 事件帧自带 32 位时间戳，**0x08/0x0A（停）与 0x09（解除）成对出现**，
> 上位机据此可直接算出"停车时刻 + 停车时长"，这正是监控系统要留档的东西。
>
> **重复帧不重复上报**：急停帧连发只报一次 `0x0A`（状态跃变才报）；
> 失联同理（`safety_stop` 置位后不再进入判据）。

> ⚠ v1.2 更正（2026-10-15，以已烧录代码为准）：`0x09` 的"解除"**不是**"收到任何显式使能就解除"——
> `0x20` 使能位=1 **只**能解除**失联锁存**（`LINKLOST`），`ESTOP`/`HWFAULT` **只有** `0x21`（任务=自主巡航）能解。
> 完整判据见 §四 表后的**锁存解除条件矩阵**（`patrol.c:124-170`）；原先"`0x20` 使能=1 或 `0x21` 即解除安全锁存"的笼统说法按矩阵作废。

## 四、下行帧（监控系统 → 机器人，命令字 0x20–0x2F）

| 命令字 | 名称 | 长度 N | 数据段定义 | 立即回复 | 间接可观测 |
|---|---|---|---|---|---|
| 0x20 | 运动控制 | 5 | 线速度 int16(mm/s)、角速度 int16(0.1 deg/s)、使能 uint8 | **无**（只改方向标志）| 周期 `0x12`（阶段/任务号）+ `0x16` 状态位 |
| 0x21 | 任务指示 | 2+2k | 任务 ID uint8、参数个数 uint8、参数 uint16×k（**k 个参数当前被忽略**）| **无** | 周期 `0x12`（阶段/任务号/完成度）|
| 0x22 | 控制模式（**已定义、未实现**）| 1 | 模式枚举：0=平衡，1=遥控，2=自主 | **无**（固件接受该帧但忽略，无状态变化）| —（当前模式见 §七 约定 14）|
| **0x23** | **巡检参数** | **12** | **见下** | **立刻回一条 `0x12`** | — |
| **0x24** | **PID 在线调参** | **6** | 参数 ID uint8、保留 uint8、参数值 float32 | **回一条 `0x24`**（回读实际生效值 / 扩展 ID 回状态）| — |
| 0x2F | 紧急停机 | 0 | 无数据段 | **无**（只置停车标志）| 周期 `0x12` + `0x13` 事件 `0x0A` |

> ⚠ v1.2 更正（2026-10-15，以已烧录代码为准）——**"机器人响应"一列已按代码拆成"立即回复 / 间接可观测"两列**：
> **① "执行后回 `0x12`"只对 `0x23` 成立。** `0x23` → `app_tasks.c:177-185` 解包成功后**立刻回一条 `0x12`**；
> `0x24` → 回一条 `0x24` 回显（`:135-144`）；而 **`0x20`（`:235-263`）与 `0x2F`（`:269-273`）只改标志、没有任何回复**；
> `0x21`（`:228` → `patrol.c:113-147`）同样**不回**任何帧。⇒ 上位机对 `0x20`/`0x21`/`0x2F` 只能**间接观测**。
> 补充：`0x24` 的回复是**有条件**的——越界/NaN/未知 ID 时 `app_tasks.c:214` 的条件不成立 ⇒ **整帧没有回复**
> （要确认旧值请另发 `0xFF` 全量回读；§3.8 表的"回读仍是旧值"指的是这一条路径）。
> **② `0x21` 的 k 个参数当前被完全忽略**：`patrol.c:118-147` 只解释 `data[0]` 的任务 ID
> （`data[1]` 的参数个数与 k 个 uint16 **收了但不用**）⇒ 参数留给后续版本，上位机不要依赖它。
> **③ `0x22` 控制模式：已定义、未实现。** 固件接受该帧但**忽略**——`patrol.c:172-173` 的 `case PROTO_DOWN_MODE: return 1;`
> 注释即"本状态机只记日志，不改安全策略"，**无状态变化、无回复**；模式枚举 `protocol.h:92-94` 在固件里**无任何使用点**。
> 当前"模式"实际由 `Flag_Stop`（按键 / `App_MotorDisable`）、`0x20` 的方向标志、`0x21` 的任务共同决定；
> 真正的"常规 / 避障（跟随）"是**厂商变量 `Bi_zhang`**，只能靠**长按按键翻转**（`control.c:328-329` ⇒ 只能取 0/1），
> 且跟随分支在 RTOS 构建下**不可达** —— 详见 §七 约定 14。
>
> **④ 锁存解除条件矩阵（★ 关键：`0x20 enable=1` 只解"失联锁存"）** ——依据 `patrol.c:124-170`：
>
> | 锁存原因（`stopReason`）| 置位点 | `0x20` enable=1 | `0x21` 任务=自主巡航（`0x01`）|
> |---|---|---|---|
> | `LINKLOST`（失联 → 事件 `0x08`）| `patrol.c:202-212`（500 ms 未收到下行帧）| ✅ **解除**（`:149-160` 要求 `stopLatched` 且 `stopReason` **恰为** `PATROL_STOP_LINKLOST`）| ✅ 解除 |
> | `ESTOP`（急停 → 事件 `0x0A`）| `patrol.c:162-170`（收 `0x2F`）| ❌ **解不开** | ✅ 解除（`:124-138` 清**所有**停车原因）|
> | `HWFAULT`（硬件/低压 → 事件 `0x05`）| `patrol.c:215-221`（`app_tasks.c:591-609` 置 `hwFault`）| ❌ **解不开** | ✅ 解除 |
>
> ⇒ 原先"`0x20` 使能=1 **或** `0x21` 即解除安全锁存"的笼统说法按本矩阵作废：
> **`0x20` 只对"失联锁存"有效**（且要求该原因未被其它原因叠加，因为判据是 `==` 而不是位与）；
> `ESTOP`/`HWFAULT` **只有** `0x21`（巡航）能解。
> ⇒ 安全推论：**`0x20 enable=1` 绝不可用作保活** —— 失联锁存期间每 200 ms 发一次，等于每 200 ms 自动拆掉一次失联保护；
> 保活应只用 `0x1F` 心跳（见 §七 约定 11）。
> ⇒ 观测提示：`0x21` 只清 `PATROL_FLT_LINK` 位（`patrol.c:130`），`HW`/`GAS` 位**不随解除清零** ⇒
> 解除后 `0x12` 的 `异常标志` 可能**仍显示硬件位**，这属正常，不要据此判"仍在故障"。

### 3.4 0x15 诊断（数据段 16 字节，v1.2 新增）

> **为什么要这一帧**：OLED 是现场唯一的可视化输出，但"屏幕画成什么样、任务还活着没有"
> 在协议里原本**完全看不到** —— 联调时只能靠人眼看屏、靠猜。这一帧把那些不可见的状态变成
> **可远程测量**的数据：`tick` 在涨 = 任务存活；`OLED 写计数` 在涨 = 屏幕确实在被刷；
> 两者都不涨/其一不涨，对应的排查方向完全不同。
> **向后兼容**：它是**新增命令**，不改动任何已有帧的长度与语义；旧工具不认识就直接忽略。

### 3.5 0x16 三环实况（数据段 20 字节，v1.2 新增）

> **为什么要有它**：调平衡时唯一可见的现象原本只有"轮子往哪转"，而三个环各自的贡献、
> 以及"算出来的值到底有没有被写进寄存器"全都不可见。速度环的权重量级是平衡环的 13 倍，
> 它一旦符号错就把平衡环的表现**完全掩盖** —— 只能反复"翻一个试试"，必然绕圈。
> 本帧把中间量全部摊开（**新增命令，不改任何已有帧**）。

| 偏移 | 字段 | 类型 | 说明 |
|---|---|---|---|
| 0 | `Balance_Pwm` | int16 | 平衡环输出（P+D）|
| 2 | `Velocity_Pwm` | int16 | 速度环输出（PI）|
| 4 | `Turn_Pwm` | int16 | 转向环输出（PD）|
| 6 | `Moto1` | int16 | 送 `Set_Pwm` 前的左轮值（含限幅）|
| 8 | `Moto2` | int16 | 右轮 |
| 10 | `CCR_A` | uint16 | **真实写进 TIM1->CCR4 的占空**（左轮）|
| 12 | `CCR_B` | uint16 | 右轮（TIM1->CCR1）|
| 14 | `EncLeft` | int16 | 编码器**原始计数**（每 10 ms，不依赖轮径标定）|
| 16 | `EncRight` | int16 | 同上 |
| 18 | 状态位 | uint8 | bit0 `Flag_Stop` / bit1 `App_MotorDisable` / bit2 **本拍真的调用了 `Set_Pwm`** / **bit3 固件特性位**（★ v1.2 新增，2026-10-15：1 = 该构建含"左右倾角上报 / 转向环启用 / 前进档 150 / MQ-135 角色指派"。**用途：同一天多次构建时 `buildId` 只到"日"，靠它才能一眼判断板上是哪一版**；上位机读到 0 会提示"旧构建，请重烧"） |
| 19 | **固件版本字节** | uint8 | **`(月 << 4)` ｜ `日`**，当前 **`0xAF`** = 10 月 15 日（见 §3.7）。原先定义为"保留"，v1.2 起改为版本字节 |

**判读要点**：偏移 6/8 与 10/12 对照 ⇒"算了没执行"（如 `Moto1=6000` 而 `CCR_A=0`）；
偏移 18 的 bit2 是"算出来≠真执行"的**直接断言位**；偏移 14/16 让上位机自己算速度，
把"轮径标定错"从"控制问题"里分离出去。

### 4.2 0x24 PID 在线调参（数据段 6 字节）

调参是本项目控制环节的关键需求（避免"改参数→重编译→重烧录"的长迭代）。

| 参数 ID | 对应基底变量 | 说明 |
|---|---|---|
| 0x01 | `Balance_Kp` | 直立环 P（默认 300） |
| 0x02 | `Balance_Kd` | 直立环 D（默认 1） |
| 0x03 | `Velocity_Kp` | 速度环 P（默认 80） |
| 0x04 | `Velocity_Ki` | 速度环 I（默认 0.4） |
| 0x05 | `Zhongzhi` | 机械中值（默认 1） |
| 0x06 | `Turn_Kp` | 转向环 P（默认 52） |
| 0x07 | `Turn_Kd` | 转向环 D（默认 0.5，仅前后运动时生效） |
| **0xFF** | — | **★ v1.0-b 扩展：请求全量回读** —— 机器人按 0x01~0x07 顺序回 **7 条** 0x24 帧 |
| **0x00** | — | **★ 扩展：保存当前参数到 Flash** —— 回一条 0x24（ID=0x00，值 0.0 表示成功）|
| **0xFE** | — | **★ 扩展：从 Flash 重新载入**（值 0.0 表示成功）|
| **0xFD** | — | **★ 扩展：调参观测模式开关**（值 1=开 / 0=关）。开启后 0x10/0x11 以 **100 Hz** 在**有线链路**上报，用于 PID 整定；机器人回一条 0x24 确认当前状态 |

> **扩展 ID 的兼容性**：0x00/0xFD/0xFE/0xFF **不是**真实增益，只在"参数 ID"字段里出现，
> **不改变 0x24 的帧格式**（仍是 N=6：ID + 保留 + float32）。
> 上位机若不认识它们，可以完全不发，协议其余部分不受影响。
>
> ✅ **已定稿冻结（决策 57，2026-10-13）**：由 B 提出（决策 46），**会签意见由 B 代拟并定稿** ——
> 理由：这 4 个 ID 已在固件实现、已进冻结测试向量、且上位机"不认识也能不用"，
> 属**向后兼容的纯增量**，没有必要为它们阻塞 C 侧的开发。实现与测试均已就位：
> `firmware/App/Task/app_tasks.c`（0x24 处理）+ `firmware/tests/param_test.c` + `tools/fw_prep/tune.py --selftest`。

**回读机制**：机器人收到 0x24 后，把**实际生效值**以同样的 0x24 帧格式回发一次，
上位机据此确认写入成功（避免"以为改了、其实没收到"）。

**掉电保存**：调好的参数需写入 Flash，否则每次重启回到初值。
B 侧实现：参数以 **float 位型**（不做定点缩放）写入 `0x08040000`（扇区 6），
带 magic + 参数个数 + 数值合理性校验；**不复用**厂商在 `0x08020000` 的旧存储区。
写入后**当场回读校验**（写 Flash 有失败可能）。详见 `firmware/App/Control/param_store.c`。

> ⚠ v1.2 更正（2026-10-15，以已烧录代码为准）——Flash 相关三条补充：
> **① `0x24` 的 `0x00`（保存）/ `0xFE`（重新载入）是破坏性 Flash 操作。** `param_store.c:52-81` 最终走到
> `STMFLASH_Write()`（`Drivers/BSP/STMFLASH/stmflash.c:41-77`）——**只要目标字不是 `0xFFFFFFFF`，就会先
> `FLASH_EraseSector()` 擦掉整个扇区、且不保存原扇区数据**（厂商注释原文），而参数区
> `CFG_PARAM_FLASH_ADDR=0x08040000` 正是**扇区 6 的起点**（`app_config.h:228`）；该操作**无权限校验、无二次确认**。
> ⇒ **不要在运动过程中或周期任务里发这两个 ID**（整扇区擦除期间 CPU 取指被阻塞——代码也在同一片 Flash 上——参数窗口会短暂失效）。
> **② Flash 参数布局**（`param_pack.c:73-102`）：`word[0] = MAGIC`（`CFG_PARAM_MAGIC` = `0x50494431`，头文件注释记作 `'PID1'`）、
> `word[1] = 参数个数`（= `PARAM_COUNT` = 7）、`word[2..8] = 7 个 float 的位型`，共 **9 字 = 36 B**
> （读写窗口取 **13 字**，多读 4 字留给将来扩展；余下字填 `0xFFFFFFFF`）。
> ⇒ **布局标识 = MAGIC + 参数个数**：`ParamPack_Unpack` 同时校验这两项，不一致即判"未写过 / 格式不符"并**退回默认值**。
> **③ ⇒ 增删参数必须同步改 `PARAM_COUNT`（`param_pack.h:34`/`PARAM_WORDS`），属破坏性变更**：
> 旧记录会被判无效、上电静默回默认值（不崩溃，但表现为"参数莫名丢失"）——改之前先想好要不要写迁移。

## 五、时序与容错

| 项目 | 约定 |
|---|---|
| 状态上行周期 | 50 ms（20 Hz） |
| 气体与环境上报 | 常态 1000 ms（1 Hz）；异常时 200 ms（5 Hz） |
| 事件上报 | 触发即发，不等周期 |
| 心跳 | 200 ms |
| 链路失联判定 | 上位机 200 ms 未收到任何帧 → 判定断开，触发重连提示 |
| 机器人侧失联保护 | 500 ms 未收到任何下行帧 → 进入安全停车 |
| 带宽核算 | 20 Hz × 约 20 B + 1 Hz × 23 B ≈ **430 B/s**，115200 bps（约 11.5 KB/s）余量充足 |

> ⚠ v1.2 更正（2026-10-15，以已烧录代码为准）——安全机制三条按代码补充/更正：
> **① 失联判定有前提：必须"曾经收到过下行帧"。** `patrol.c:202-212` 的失联分支入口条件是 `st->linkSeen && !st->safetyStop`，
> 而 `linkSeen` 只由 `Patrol_NoteDownlink()`（`:105-109`，收到任一 CRC 合法下行帧时调用）置位。
> ⇒ **上电后从未连过上位机时，机器人不会自己锁存安全停车**（不会"因为没人跟它说话就停在原地"）；
> 反之只要连过一次，之后 500 ms 静默即锁存。
> **② 锁存解除按矩阵**（完整表见 §四 表后）：`LINKLOST` → `0x20 enable=1` **或** `0x21`（巡航）；
> `ESTOP`/`HWFAULT` → **仅** `0x21`（巡航）。⇒ **`0x20 enable=1` 不可用作保活**（那会周期性拆掉失联保护）。
> **③ 低压保护有两条独立通路，App 侧那条不会自动恢复**：
> · **控制侧迟滞**（`control.c:355-373`，中断每拍执行）：低于 11.10 V **连续 50 拍**才锁存 `s_lowBatLatched`，
> 回到 **≥ 11.60 V** 才解除 —— 它只恢复 `Turn_Off()` 的判据（即电机能否出力），**不解除任何 App 层锁存**；
> · **App 侧锁存**（`app_tasks.c:591-609` → `patrol.c:215-221`）：先过"有电池"门槛 `CFG_BAT_PRESENT_MIN` = **6.00 V**，
> 再低于 `CFG_BAT_LOW_LIMIT` = **11.10 V** 连续 `CFG_BAT_LOW_CONFIRM` = **5 拍** ⇒ 置 `hwFault` ⇒ `safety_stop(HWFAULT)` 锁存。
> ⇒ **App 侧锁存必须由上位机显式重下任务（`0x21` 巡航）才能解除**（`HWFAULT` 只有 `0x21` 能清，见 §四 矩阵）；
> 且**若电压仍低于门槛，重下任务后可能立刻再次锁存（回弹）** —— 解除前应先确认电压已回升
> （`0x15` 偏移 0 的 0.01 V 电压值）；控制侧 ≥ 11.6 V 的"恢复"只说明电机允许出力，**不代表锁存已解除**。

### 5.1 数据表示约定

- **字节序：小端**（与 ARM 默认一致）；
- **浮点数据放大为定点整数传输**（如角度 ×100 后存 int16），避免跨平台浮点表示差异；
- 唯一例外是 0x24 调参帧的参数值，直接用 float32（便于上位机传任意增益，且调参对精度要求高）；
- 所有无符号量用 `uint*`，有符号量用 `int*`（负数按二进制补码）。

### 3.6 0x20 运动指令的实现与安全（2026-10-13 起真正生效）

- **数据段（N=5）**：`[0..1] linMmS(int16, mm/s)`、`[2..3] angDpsX10(int16, 0.1 dps)`、`[4] enable`。
- **实现语义**：固件沿用厂商的"**方向标志 + 固定速度档**"模型，连续量只做**方向判定**：
  `|linMmS| ≥ 50` 判前进/后退；`|angDpsX10| ≥ 100`（10 dps）判左/右转；`enable=0` 立即停。
  （厂商的 `velocity()` 读 `Flag_Qian/Hou`、`turn()` 读 `Flag_Left/Right`，本实现就是写这四个标志。）
- **★ 安全看门狗**：**超过 500 ms 没收到新的 0x20 ⇒ 自动全部清零（停）** ——
  避免"上位机崩溃/链路断开，车还按最后一条指令一直跑"。
- **执行反馈（⚠ v1.2 更正，2026-10-15，以已烧录代码为准）**：`0x20` 本身**没有任何回复**，只能**间接观测** ——
  任务状态 `0x12` 与 `0x10`/`0x11` **同频**（每拍上报，标称 50 ms，实测约 15 Hz；原写"5 Hz 周期上报"有误，见 §三）；
  `0x16` 的三分量与状态位可进一步确认"指令是否真的到了执行器"。
- **★ 锁存解除**：`0x20` 使能位=1 **只**能解除**失联锁存**（`LINKLOST`）；`ESTOP`/`HWFAULT` **只有** `0x21`（巡航）能解 ——
  完整矩阵见 §四 表后的"锁存解除条件矩阵"（`patrol.c:124-170`）。

### 3.7 固件版本字节（0x16 偏移 19）

`0x16` 的**保留字节**（偏移 19）用作**固件版本**，取值 `(月 << 4) | 日`（如 10 月 15 日 = `0xAF`）。
工具/上位机应把它显示出来 —— 联调时"到底烧没烧上"曾扯误一整轮，这一字节是**可验证性**的基础设施。

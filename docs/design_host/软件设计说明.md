## 1. 概述与范围

上位机是"仓储环境安全巡检机器人"的**监控与操作台**：把下位机（STM32 平衡小车）通过**有线串口**与
**蓝牙**两条链路送上来的二进制帧，变成**人能一眼读懂的界面**，并提供**操作入口**（任务下发、急停、
解除锁存、在线调参）与**记录能力**（逐帧 CSV、会话库、回放）。

| 做什么 | 不做什么（边界） |
|---|---|
| 解帧 → 单位换算 → 状态聚合 → 显示/告警/记录 | **不做控制律**：平衡、避障、安全停车全在固件里 |
| 下行命令的**数据段**构造（进协议、带钳位） | 不代替固件判断"能不能动"（固件是安全责任方） |
| 保活心跳（防固件 500 ms 失联锁存） | 不绕过任何安全逻辑（**尤其不用使能类命令保活**，见 §6.2） |
| 记录与回放（现场复盘、无硬件演示） | 不做数据拟合/预测（只如实呈现与标注） |

## 3. 总体架构：五层单向依赖

```
                ┌────────────────────────────────────────────┐
                │  ui/        界面层（Qt Widgets + QCustomPlot）│
                │  只读 domain 的状态，只调 commands 构造下行    │
                └───────────────▲───────────────┬────────────┘
                                │ 状态/告警      │ 用户操作
                ┌───────────────┴───────────────▼────────────┐
                │  data/      记录与落盘（CSV / SQLite / 事件流）│
                └───────────────▲───────────────┬────────────┘
                                │               │
                ┌───────────────┴───────────────▼────────────┐
                │  domain/    领域层（单位/帧/状态/告警/命令/保活）│
                │  ★ 协议口径的**唯一**落点：所有 0.1 与 10 在这里 │
                └───────────────▲───────────────┬────────────┘
                                │ 帧(载荷)       │ 下行数据段
                ┌───────────────┴───────────────▼────────────┐
                │  io/        链路层（真实串口 / 蓝牙 / 假源 / 回放）│
                │  读线程解帧 → 跨线程队列信号                    │
                └───────────────▲───────────────┬────────────┘
                                │ 字节流         │
                ┌───────────────┴───────────────▼────────────┐
                │  protocol/  协议层（纯 C++/Qt Core，无界面依赖）│
                │  CRC-16/MODBUS、流式解帧、组帧、命令字常量       │
                └────────────────────────────────────────────┘
```

**依赖方向**（唯一合法方向，`CMakeLists.txt` 用 5 个 target 强制）：

```
protocol ← io ← domain ← data ← ui ← host(main.cpp 装配)
```

| 层 | target | 允许依赖 | 关键纪律 |
|---|---|---|---|
| protocol | `protocol` | Qt6::Core | **零界面、零全局状态**；同一份代码被 PC 单测与固件交叉验证（决策 36） |
| io | `hostio` | protocol | 真实链路与假源**同一个 `LinkBase` 接口**（决策 32）；假源必须自己走解帧（决策 30） |
| domain | `domain` | protocol, io | **单位换算只此一处**（决策 65：少一个 10 的教训）；只有 `VehicleState::dataUpdated` 才代表"新数据"（去重，决策 67） |
| data | `hostdata` | domain, io, Qt6::Sql | 写盘失败必须可见；SQLite 不可用要**降级而不是崩** |
| ui | `hostui` | data, domain, io, QCustomPlot | **界面不解析字节、不做判据**，只显示与转发；三处口径不一致的现象一律视为缺陷（决策 65） |
| host | `host` | hostui | `main.cpp` 只做装配与命令行（依赖由外向内注入） |

## 4. 线程与数据流

```
串口读线程                    主线程（GUI）
──────────                    ──────────────────────────────────────
readAll() → FrameDecoder::feed()
   ↓ 解出一帧
emit frameReady(cmd, payload) ──┐  (Qt::QueuedConnection，载荷按值传递)
                                │
                                ├→ domain::VehicleState::onFrame
                                │     · 长度/命令字校验 → 计数（格式错帧/协议外命令）
                                │     · **跨链路去重**（同命令字 + 逐字节相同 + 另一条链路 + ≤150 ms）
                                │     · 新数据才 emit dataUpdated(cmd)
                                │         ├→ AlarmEngine::onFrameDecoded（阈值类规则）
                                │         ├→ 曲线面板采样（每帧一次）
                                │         └→ 调参页 0x24 回读比对
                                ├→ data::EventLog（0x13 事件 + 本机告警 + 操作员动作）
                                └→ data::CsvRecorder（逐帧一行，含原始帧 HEX）

主线程定时器：
  10 Hz  alarm.tick()      —— 依赖"时间"的规则（失联、锁存）
  10 Hz  各面板 refresh()  —— 界面刷新（**绝不每帧重绘**）
  5 Hz   KeepaliveEngine   —— 默认 200 ms，发 0x1F 心跳（防失联锁存）
```

**为什么这么分**（三条都是踩过坑才定下来的）：

1. **解析在工作线程、判据在主线程**：串口是 IO 阻塞的，界面不能卡；但告警/记录需要统一的口径，
   所以解帧后立刻把"干净载荷"交给主线程，所有判据只出现在一处。
2. **`dataUpdated` 是"新数据"的唯一信号**：两条链路都发同样的帧（协议 §七 约定 6），
   若按"收到帧"计数，曲线会采两个样、告警的"连续 3 帧"会被 1.5 次真实采样满足（提前报警）。
3. **重绘与采样解耦**：采样每帧一次（数据点不丢），重绘 10 Hz（不卡界面）——
   `ScopePlot` 内部是环形缓冲 + 窗口 2 倍裁剪。

### 5.6 四处"判读谓词"（放在 domain，可单测）

| 谓词 | 判据 | 界面表现 |
|---|---|---|
| `LoopData::differentialWithoutTurn()` | `Turn==0` 且 `moto1 != moto2` | 红灯"Turn=0 两轮不同"（差速/极性 bug，本机曾因此原地转圈） |
| `LoopData::executionState()` | `Moto≠0 而 CCR==0` 时：`Flag_Stop`/电机被禁 ⇒ **Protected**；否则 **Mismatch** | 琥珀"保护中，未驱动" vs 红"算了没执行"（决策 74） |
| `tiltProtectActive(pitch, zhongzhi)` | `|倾角−Zhongzhi| > 40°` | 琥珀提示（现场手动倾车也会触发，**不是故障**） |
| `LoopData::featureBits()` | `0x16` 状态位 **bit3 = 固件特性位**（决策 79） | 状态条 `固件 0xAF/10-15 · 新特性✔` / `· ⚠旧构建`（未置位 ⇒ 板上是旧构建，提示重烧） |

> **另两处"如实标注"**（不属于谓词，但同属"监控端口径"）：`0x11` 的电机输出均值按固件换算关系显示为
> **带符号估算占空比**（`Moto ÷ 7179.5 × 100`，见 `units.h`；**负值 = 反向、不报警**，只有 `|Moto|>7179`
> 即 CCR 被 8400 截断时才提示"已顶到满量程"）；**偏航角固件未计算** ⇒ 界面写"固件未计算（该字段恒 0）"，
> 不把常量 0 当成测量值；同理左右倾角注明是**仅加速度计的静态角**。

## 6. 关键设计决策（摘录，完整见 [`../决策记录.md`](../决策记录.md)）

### 6.1 协议口径只在一个地方

`units.h` 是"协议定点量"的唯一换算处。为什么值得单独一条：**少除一个 10** 曾让湿度 66 % 显示成 6 %，
而**界面上看起来完全正常**（决策 65）。同理 `expectedUpLen()` 是精确长度表，长度不符就计
"格式错帧"而不是硬解 —— 错误必须能被计数，才有资格被修。

### 6.2 保活只能用心跳（安全相关，铁律 40）

固件规则：**500 ms 没有下行帧 ⇒ 安全停车并锁存，硬件按键也解不开**。所以上位机必须周期发合法下行帧。
但协议同时规定：**收到显式使能（`0x20` 使能位=1 / `0x21` 自主巡航）即解除安全锁存**。
⇒ 若用"使能"当保活，等于每 200 ms 自动拆掉一次急停保护，而界面一切正常（铁律 29 的旁路）。
本项目：`KeepaliveEngine` 默认 `0x1F` 心跳、200 ms（2.5 倍余量）、链路不通**不发**、
发送失败不计入"已发"；界面把"使能保活"做成需要显式选择并红字告警的选项（决策 69）。

### 6.3 判据必须与固件同口径（铁律 42）

P4 对齐真机时连中两次：**参数范围**照协议表写成 `0~500`，而本机正确值是 **−80/−0.4**（负增益，
因为电机/编码器符号与厂商约定相反）⇒ 前端校验会把板子上的正确值判为非法；**低压报警**只看
`<11.1 V`，而固件对"没接电池/分压悬空"有 **6.00 V 门槛** ⇒ USB 供电时界面报红而车只是没接电池。
现：范围允许负值（带回归测试）、低压先过 6 V 门槛、解除线取 **11.6 V**（与固件一致）。
**规则**：写任何前端判据前先读 B→C 接口口径文档，并用 `--probe-readback` 拿真机数据核对。

### 6.4 报警要指向真问题

"监控台的价值在于如实"：报警判据过宽会让现场第一反应变成"这软件又乱报"，
之后真故障也不信（狼来了）。所以：保护生效（未使能时 `CCR=0`）标琥珀而不是红；
`0x11` 的 PWM 字段真机上报带符号电机输出（−1579）时**标注"超出协议约定"**，
但**不擅自截断**（截断会掩盖协议偏差）。

### 6.5 记录与回放共用一条通路

CSV 的最后一列是**原始帧 HEX** ⇒ 回放时把这一列喂回解帧器（与真实链路同一套解析/聚合路径），
于是"记录→回放"不需要第二套格式，也不可能出现"记录对了、回放不对"（决策 30/32 的延伸）。

## 7. 协议一致性

| 方向 | 命令 | 载荷长度 | 周期（协议标称 → **实测**） | 上位机用途 |
|---|---|---|---|---|
| 上行 | `0x10` 姿态 | 12 | 20 Hz → **≈15 Hz** | 总览姿态卡 + 地平仪 |
| 上行 | `0x11` 运动 | **9** | 20 Hz → **≈15 Hz** | 轮速/PWM/超声/避障位；★ 距离字段单位是 **mm**（界面 /10 显示 cm，`units::cmFromMm`）；★ PWM 字段是**带符号电机输出均值**（≈±8200）而非千分比 |
| 上行 | `0x12` 任务 | 5 | **与 `0x10/0x11` 同频**（代码事实：共用同一 telemetry 节拍；非 5 Hz） | 巡检阶段/进度/巡检点/异常 |
| 上行 | `0x13` 事件 | 5 | 事件触发 | 事件流（已去重） |
| 上行 | `0x14` 环境 | 16 | 1 Hz | MQ-2/MQ-135/温湿度/就绪位 |
| 上行 | `0x15` 诊断 | 16 | 1 Hz | 电压/页号/堆/OLED 写速率/任务 tick |
| 上行 | `0x16` 三环 | 20 | 1 Hz | 三环曲线 + `Moto/CCR` 对照 + 状态位 + **固件版本** |
| 上行 | `0x1F` 心跳 | 0 | **200 ms（5 Hz）**（代码事实，非 1 Hz） | 存活 |
| 上行 | `0x24` 回显 | 6 | 命令触发 | 调参回读/回执（**只读全量回读 0xFF**） |
| 下行 | `0x20` 运动 | 5 | 10 Hz | 遥控（按住走松手停，`enable=0` 立即停）；★ `enable=1` **只解"失联锁存"**（急停解不开；无回复） |
| 下行 | `0x21` 任务 | 2+2k | 事件 | 巡航/返航/待机；★ **k 个参数被固件忽略**（只解释任务 ID）；★ 唯一能解**急停/硬件故障**锁存的命令 |
| 下行 | `0x22` 模式 | 1 | 事件 | ⚠ **固件未实现**：接受即忽略、无回复；避障/跟随目前只能靠板上长按按键 |
| 下行 | `0x23` 巡检参数 | 12 | 事件 | 采样周期/阈值/自适应/补偿/确认帧数；**唯一会立刻回 `0x12` 的命令** |
| 下行 | `0x24` 调参 | 6 | 事件 | PID 写入/Flash 保存/载入/观测模式/全量回读；★ `0x00`/`0xFE` 是**破坏性 Flash 操作**（整扇区擦除），别在运动中发 |
| 下行 | `0x2F` 急停 | 0 | 事件 | 停车并锁存（只能 `0x21` 解除；**无回复**） |
| 下行 | `0x1F` 心跳 | 0 | **5 Hz** | 保活（防失联锁存） |

**实测/口径偏差（已按代码更正并交 B）**：`0x12` 与 `0x10/0x11` 同频；`0x1F` 心跳 200 ms；
`0x11` 的 PWM 字段是带符号电机输出、**距离字段是 mm（协议原写 cm，差 10 倍）**；
`0x24` 回读的 `Velocity_Kp/Ki` 当前是 `+80/+0.4`（编译期定稿 `−80/−0.4` **被参数范围校验拒绝**，见 §6.3 与决策 77）。
详见 [`C部分方案与计划.md`](C部分方案与计划.md) §十六。

## 10. 构建与打包

```powershell
# 开发（Debug，便于 gdb）
cmake -S host -B host/build -G Ninja -DCMAKE_BUILD_TYPE=Debug && cmake --build host/build
# 交付（Release：host.exe 3.2 MB，而 Debug 是 41.5 MB）
cmake -S host -B host/build-release -G Ninja -DCMAKE_BUILD_TYPE=Release && cmake --build host/build-release
ctest --test-dir host/build-release --output-on-failure
# 一键打包（windeployqt + 瘦身 + 四项校验，产出 host/dist/上位机/）
pwsh -File host/package.ps1
```

打包脚本的**四项校验**（缺一项都不算成功）：① 干净 PATH 下无头自检退出码 0；
② 界面真的起来且 4 s 不异常退出；③ 截图链路（渲染 → `grab` → PNG 落盘）；
④ 记录链路（CSV 行数 + **SQLite 会话库真的建起来**）。
产出 **12 个文件 / 37.4 MB**（windeployqt 原始 109 MB，删掉 D3D12 着色器编译器、QML/网络/SVG、
多余 SQL 驱动与图片格式插件 —— 每一项都是"删了再验"确认不需要）。

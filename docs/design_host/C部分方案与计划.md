## 二、调研：可借鉴的成熟方案（GitHub / 公开资料）

### 2.1 首要参考：[Serial Studio](https://github.com/Serial-Studio/Serial-Studio)（开源遥测仪表盘，Qt6）

**为什么它是本项目的头号参考**：目标和我们的几乎一样 —— "把串口/蓝牙来的数据变成实时仪表盘"，而且它的**分层方式已经被大规模使用验证过**（官方文档自述解析流水线可跑 256,000 帧/秒、渲染 60 FPS，且以 CI 基准门约束）。

| 借鉴点 | 它的做法 | 我们怎么用 |
|---|---|---|
| **数据流分层** | 驱动层（UART/BLE/TCP）→ 帧解析器 → 逐数据集变换（EMA/标定/单位换算）→ 部件（plots/gauges/maps）见 [Data Flow](https://serial-studio.com/help/data-flow) | 我们**照这个顺序分层**：`io/` → `protocol/`（已有）→ `domain/`（变换+告警判定）→ `ui/`。**变换绝不写在界面里** |
| **"描述一次，界面围绕它生成"** | Project 文件定义 groups/datasets/widgets，编辑器改表单即可 | 我们的协议是**固定**的，不需要项目编辑器；但把这套思想用在**图表通道配置**上：谁画哪条曲线由一份配置表决定，不散落在 UI 代码里 |
| **部件清单（可直接抄的"该有什么"）** | 折线图、仪表盘、条形、GPS 地图、FFT、加速度/陀螺/罗盘、数据表格、**LED 面板**、终端、多通道图 | 我们取：折线（气体/电压）、**仪表盘（速度/倾角）**、数据表格（当前值）、**LED 面板（状态位/故障位）**、**终端（原始帧日志/调试）** —— 正好覆盖任务书"实时监测 + 报警 + 状态" |
| **记录与回放** | CSV 导出；**Historian：把帧与原始字节记进 SQLite**，可浏览/标注/回放 | 我们做 **CSV（逐帧一行）+ SQLite（会话与事件）**；回放是演示与复盘的杀手锏 |
| **性能预算** | 解析 256k fps；渲染 60 FPS | 我们的实际负载：周期帧 ~60 帧/s（0x10+0x11 各 20 Hz、0x12 5 Hz、0x14 1–5 Hz、0x1F 5 Hz）。**留 100 倍余量**，所以 UI 卡顿一定是架构问题，不是性能不够 |
| **Qt 模块清单** | QtCore/Gui/Widgets/**QtGraphs**/Svg/Sql/**SerialPort**/Bluetooth | 我们的选型可直接对齐（见 §三）|

> ⚠️ **不要照搬的部分**：它的 Project 编辑器、JS/Lua 脚本解析、多协议驱动（Modbus/CAN/OPC UA）、TCP/gRPC API —— 与课程任务无关，**加上去只会增加风险**。我们只借"分层 + 部件分类 + 记录回放"这三样。

### 2.2 第二参考：中文工业上位机项目

- [gccnb/industrial-multiprotocol-debugger](https://github.com/gccnb/industrial-multiprotocol-debugger)（C++/Qt，RS485 ASCII / Modbus RTU / CRC / **报文日志** / **设备模板** / **SQLite 保存**）——
  它的"**报文日志 + 设备模板 + SQLite**"三件套正是调试型上位机的骨架：我们照此做**原始帧日志面板**与**参数表（模板）**，调参时能一眼看到"发了什么、回了什么"。
- 同一类项目反复出现的一个**打包坑**：[灯光控制上位机示例](https://blog.csdn.net/ik678901234/article/details/162777922) 明确记录"SQLite 文件路径必须用相对路径/标准路径，否则打包后不可用" → 我们用 `QStandardPaths::AppDataLocation`（见 §五）。

### 2.3 UI 与"美观"：用规范，而不是凭感觉

- **ISA-101（工业人机界面标准）**（[概要](https://www.htmlelements.com/industrial/docs/isa101/index.html)）给了可执行的审美判据，而不是"我觉得好看"：
  1. **背景低饱和中性灰**，正文用高对比中性色；**颜色只用于表达"异常"**（正常状态不要用彩色）；
  2. **不要渐变、阴影、3D、立体边框**（它们占用注意力却不携带信息）；
  3. **同一量始终保持同一位置与量程**（操作员靠"位置"读值，不靠"找"）；
  4. 层级用**灰阶 + 字重**表达，而不是用更多颜色。
  > 这条对课程评分其实很友好：**"好看"变成了"有依据"** —— 答辩时可以指着规范说明"为什么报警用琥珀色、正常用灰色"。
- **工作区布局**：用 `QDockWidget` 做可停靠/可重排的多面板（[进阶用法](https://awesome-embedded-learning-studio.github.io/Tutorial_AwesomeQt/advanced/03-qtwidgets/59-qdockwidget-advanced)），并保存/恢复布局（`saveState()`/`restoreState()`）—— 演示时能切换"监测视图 / 调参视图"。
- **主题**：QSS 变量化暗色主题（参考 [Qt Material](https://qt-material.readthedocs.io/) 的配色思路），**不引入重量级第三方皮肤库**（避免打包与许可问题）。

### 2.4 曲线控件选型（本项目最容易选错的一处）

| 方案 | 优 | 劣 | 结论 |
|---|---|---|---|
| **QCustomPlot**（三方，单文件 .h/.cpp，GPL） | 实时曲线性能好、API 直白、**无额外 Qt 模块依赖**、示例多 | 三方库需自带源码（约 1 万行）| ✅ **选它**（我们帧率低、但要求"曲线顺滑可缩放"，它最省事）|
| Qt Charts（官方，GPL/商业双授权） | 官方模块 | Qt6 中已被 **Qt Graphs** 取代，社区资料新旧混杂 | 🔶 备选 |
| **Qt Graphs**（Qt 6.6+ 官方新一代） | 官方、支持 2D/3D、性能好 | **依赖 QML/Quick 组件**，Widgets 集成与文档仍新，踩坑成本高 | 🔶 不选（交给"想用 QML 重写"的将来）|

> 参考：[Qt Graphs/Charts 数据添加的性能陷阱与 QCustomPlot 替代方案](https://runebook.dev/zh/docs/qt/qml-qtgraphs-pieseries/added)、[从 Qt Charts 到 Qt Graphs 的迁移与 QCustomPlot 实战](https://runebook.dev/zh/docs/qt/qtgraphs-index)。**结论：在 Widgets 体系里，QCustomPlot 是风险最低的选择。**

### 2.5 串口读取的正确姿势（避免 UI 卡顿）

Qt 官方给了两种范式（[阻塞接收器示例](https://doc.qt.io/qt-6.8/zh/qtserialport-blockingreceiver-example.html)）：事件驱动（`readyRead` 信号）与阻塞式（`waitForReadyRead`）。我们**用后者跑在独立线程里**：

- 串口读取线程：`waitForReadyRead(超时)` → 读字节 → 塞进**自有环形缓冲**；
- 解析也放在该线程（或在第二个工作线程）：`Proto_Feed` 解帧；
- 解出的**结构体**通过 `Qt::QueuedConnection` 信号发给 UI（**不跨线程共享缓冲**）。
- 理由：事件驱动 + 高频时容易"每几个字节触发一次信号"，反而更抖；阻塞式线程配合队列连接，UI 天然不被拖住。

| 项 | 选型 | 理由（一句话） |
|---|---|---|
| 框架 | **Qt 6.11.2 Widgets（C++20）** | 与现有 `host/` 一致；Widgets 生态的曲线/表格/停靠面板最成熟；不引入 QML 学习成本与集成风险 |

## 四、模块规划（分层 + 目录）

> **铁律：依赖单向向下**（与固件侧同一条纪律，见 [`../design_firmware/编码规范.md`](../design_firmware/编码规范.md)）。
> 界面层**不许**直接碰串口；解析层**不许**知道界面的存在。

```
host/
├── src/
│   ├── protocol/        【已有】CRC、组帧/解帧、字段结构体          ← 无 Qt GUI 依赖（可单测）
│   ├── io/              ★新增：链路抽象
│   │   ├── link.h            抽象接口：open/close/write/signals(bytes, state)
│   │   ├── serial_link.*     QtSerialPort + 工作线程（阻塞读 → 环形缓冲）
│   │   └── link_manager.*    两条链路（有线/蓝牙）统一管理、自动重连、链路统计
│   ├── data/            ★新增：数据层
│   │   ├── session.*         一次连接会话：开始/结束、帧计数、时间轴
│   │   ├── recorder.*        CSV 逐帧落盘（含列定义与版本）
│   │   ├── event_log.*       事件流（0x13）落盘 + SQLite
│   │   └── param_store.*     参数快照（0x24）历史，便于对比"调参前后"
│   ├── domain/          ★新增：领域层（纯逻辑，可单测，不依赖 Qt Widgets）
│   │   ├── vehicle_state.*   姿态/运动/任务/环境的**当前状态聚合**
│   │   ├── alarm.*           告警判定与迟滞（气体阈值、低压、失联、锁存）
│   │   └── units.*           单位换算与显示格式（ppm×10 → ppm、0.01° → °、0.01V → V）
│   ├── ui/              ★扩充
│   │   ├── mainwindow.*      主窗：菜单/工具栏/状态条/停靠布局
│   │   ├── panels/           各面板（见 §六）
│   │   ├── widgets/          自绘小部件（LED 状态灯、仪表盘、数值牌）
│   │   └── theme/            QSS 主题与配色变量
│   └── app/             ★新增：装配层
│       ├── main.cpp          组装依赖（link → 解析 → domain → ui）
│       └── settings.*        端口/波特率/阈值/布局的持久化（QSettings）
└── tests/               ★扩充：协议（已有）+ domain + data + UI 冒烟
```

**每层职责一句话**：
- `io/`：**只搬字节**（含重连、统计），不理解语义；
- `protocol/`：**只认帧**（校验、字段解析），不碰硬件也不碰界面；
- `domain/`：**只算语义**（状态机镜像、告警、单位），纯函数优先 → 可单测；
- `ui/`：**只显示与下发**；
- `app/`：**只做装配**。

## 五、数据与线程模型（关键设计）

```
[串口线程 A: 有线]  waitForReadyRead ─┐
                                     ├─→ 环形缓冲 ─→ Proto_Feed(解帧) ─→ 结构体
[串口线程 B: 蓝牙]  waitForReadyRead ─┘                                     │
                                                                            ▼
                              Qt::QueuedConnection 信号（值语义，跨线程安全）
                                                                            │
                        ┌───────────────────────────────────────────────────┤
                        ▼                                                   ▼
                  domain::VehicleState（合并两路，按时间戳去重）         data::Recorder（CSV/SQLite）
                        │
                        ▼  （UI 定时器 20 Hz 拉取，**不是每帧重绘**）
                   UI 面板（曲线/仪表/表格/日志）
```

三条设计决策及其理由：
1. **UI 以 20 Hz 定时刷新**（而不是"每来一帧就重绘"）：人眼分辨不出 50 Hz 与 20 Hz 的刷新差别，但 CPU 差别很大；曲线用**环形数据缓冲（固定窗口，如 600 点）**避免无限增长。
2. **两路链路在 domain 层合并**：周期帧两路都发（协议 §七 约定 6），界面显示"最后一次有效值 + 该值来自哪条链路 + 两条链路各自的帧计数"，**避免"两条链路的数据互相打架"**。
3. **原始字节也要能看**：终端面板显示十六进制收发流水（可暂停/过滤），这与 §2.2 的"报文日志"一致 —— 调参和排障时它是第一现场。

**记录落盘**：
- CSV：`timestamp_ms, cmd, <字段...>`，列定义写进文件头（自描述，Excel 直接开）；
- SQLite：`sessions(id, start, end, note)`、`events(ts, code, text)`、`params(ts, id, value)`；
- 路径：`QStandardPaths::writableLocation(AppDataLocation)`（**不写死绝对路径**，见 §2.2 打包坑）。

### 6.2 美观设计（照 ISA-101，逐条可验收）

| 项 | 规定 | 验收方式 |
|---|---|---|
| 底色 | 中性深灰 `#1E2227`，面板 `#262B31`，分隔线 `#3A4048` | 截图取色 |
| 正文 | 主文字 `#E6E9ED`；次要 `#9AA3AD` | 对比度 ≥ 4.5:1 |
| **语义色（只用于异常）** | 正常=中性；**警示**琥珀 `#E0A800`；**报警/危险**红 `#D9534F`；**离线/未知**灰 `#6C757D`；**运行正常**绿 `#3FA45B`（仅状态灯） | 每个颜色在界面里有且只有一个含义 |
| 数字 | **等宽数字**（`Consolas`/`JetBrains Mono`），右对齐，固定小数位与单位 | 数值跳动时不"抖列" |
| 图表 | 网格 `#2E343B` 细线；曲线 2 px；**不用渐变填充**（最多 10% 透明面积色） | 截图 |
| 禁用 | 不出现 3D、阴影、圆角超过 6 px 的卡片 | 目视 |

### 11.5 待集成：串口/蓝牙端口自动识别（2026-10-13 真机联调提出）

现状：`tools/fw_prep/bt_scan.py` 已在 PC 侧实现"**按合法帧判定哪个口是我们的设备**"（Windows 蓝牙 SPP 口号随机、名字不可信，靠名字猜很容易发错口）。
上位机侧要做的等价能力（写进 P1 的通信链路面板）：
1. 端口列表标注类型（蓝牙 / USB 串口）与 VID:PID；
2. 一键"自动识别"：逐个口按当前波特率试读，按 **CRC 通过的整帧数**排序并推荐；
3. 识别时必须显式驱动 **DTR=高 / RTS=低**（AGENTS 陷阱 33：否则 MCU 停在 BootLoader，
   一个字节都收不到，会被误判成"没烧进去"）；
4. 识别结果可一键填入两条链路（有线 / 蓝牙），并记住上次选择；
5. **第一件事是读固件版本字节**：`0x16` 偏移 19 = `(月<<4)|日`（当前 `0xAF` = 10 月 15 日）。
   联调时"到底烧没烧上"曾扯皮一整轮，这一字节是**可验证性的基础设施**（决策 64）；
6. **必须处理"失联锁存"**：静默 >500 ms ⇒ 板子锁存安全停车、**硬件按键也解不开** ⇒
   上位机要**持续使能/保活**（≤200 ms 一次 `0x20 enable=1` 或心跳），并在界面显式提示"已锁存、需重下任务"；
7. **`0x15` / `0x16` 两个新上行帧建议在 P1 就接上**：`0x15` 的 **OLED 写计数**（不涨=屏幕没在刷）
   与四任务 tick（在涨=任务存活）、`0x16` 的 `Moto` vs **真实 CCR**（"算了没执行"）与**编码器原始计数**，
   是把"只有人眼可见"的故障转成可远程测量的关键（协议 §3.4/§3.5、§七 约定 12/13）。

> ⚠️ **蓝牙现状（2026-10-15 实测）**：Windows 蓝牙 SPP **能配对但建不出 COM 口**；
> Python 的 `AF_BLUETOOTH` **在 Windows 上不可用**、`pybluez2` 在 Python 3.13 上编译不过；
> 本 Qt 套件**未安装 Qt Bluetooth 模块** ⇒ **P1~P5 的联调主线一律走有线（USART1）**，
> 蓝牙只作为"另一条同协议链路"保留接口（决策 45）。

### 11.6 协议 v1.2 增补的两个上行帧（C 侧实现要点，2026-10-15）

| 帧 | N | 周期 | C 侧要点 |

### 14.2 本轮修掉的一个**数据正确性缺陷**（比界面 bug 严重）

**现象**：`--selftest` 的事件流里每条机器人事件都出现**两遍**；进一步检查发现告警的"连续确认 3 帧"其实被 **1.5 次真实采样**就满足了。

**根因**：协议 §七 约定 6 规定"**周期帧两路都发**"—— 同一次物理测量会在两条链路上各来一帧。原先 `VehicleState` 只是"谁后到就用谁的值"，而下游（曲线采样、告警连续确认、事件流）都是**按帧计数**的，于是同一次测量被算了两次。

**修法（决策 67）**：去重放在**聚合层一次做完** —— `VehicleState` 为每个命令字记住"最近一帧的原始数据 + 来源 + 时刻"，判据是
**同命令字 + 内容逐字节相同 + 来自不同链路 + 间隔 ≤150 ms**（同一条链路连发两帧相同内容在 20 Hz 下很常见，**不算**重复）。
`dataUpdated`（"这是一次新测量"）与 `eventReceived` 只在非重复时发出，曲线/告警/事件流因此自动各得一次。
同时加了一个可观测的计数 `duplicateFrames`（总览页与自检输出都会显示），去重了多少条一眼可见。

**连带修掉的坑**：假源两条链路各自生成事件帧时用了各自的 tick 时刻 ⇒ 同一次冲高造出两帧**内容不同**的 `0x13`，去重认不出来。现在冲高事件的时间戳取**窗口起点**，两条链路造出的是**逐字节相同**的帧（真实固件本来就是同一帧发两路）。

### 14.3 设计取舍（写清楚，免得后来人改错）

| 取舍 | 选择 | 理由 |
|---|---|---|
| 阈值线画在哪 | **界面画线，判定在 domain** | 两套判据一定会打架；界面只负责把"阈值"和"当前值"画在一起 |
| "同一段异常只提示一次" | **状态跃变才报**；回到正常（连续确认）后**再次超限会重新报** | 计划原文"再次进入异常不再重复提示"按"重复帧不重复提示"实现 —— 若真的"再也不报"，安全功能就是装饰（AGENTS 铁律 29 的同一类错误） |
| 曲线通道排布 | **通道独立**（每通道一张图），不是全叠一张 | 厂商 PC 工具的做法；气体两个量量程不同，叠在一起读不出小变化 |
| 采样与重绘 | 采样**每帧一次**（`dataUpdated`），重绘 **10 Hz** 定时器 | 按定时器采样会**重复采样**（同一帧被记两次），按帧重绘又会卡（计划 §五） |

| 事件流吃原始帧还是吃事件 | 吃 `VehicleState::eventReceived`（**已去重**） | 直接吃原始帧就会出现"每件事两遍"（本轮实际发生） |
| QCustomPlot | 内置源码（GPLv3，未改动）+ 只对该目标关告警 | 决策 58 的选型；第三方告警不该混进"自研代码零告警"的自检里 |
